spec §3.1 — layer ownership

Layers and vertical paths

sensor_ecu and cluster_ecu are two separate Ubuntu processes, each with its own address space, PID, and memory — never one shared box — so the layer diagram is drawn as two subgraphs, one per ECU, matching that fact directly instead of a caveat underneath a merged picture.

Both ECUs happen to link the identical bsw_mcal/bsw_ecuab library source (same IoHwAb.c, same Can.c) — that is why the two subgraphs look structurally identical — but each ECU's static configuration (IoHwAb_ConfigSensor vs. IoHwAb_ConfigCluster) determines which leaf nodes it actually populates: SensorEcu never has a Display node reachable, ClusterEcu never has Adc/Dio reachable. That is a real build fact (each binary's CMakeLists.txt target links the whole library, so the unused half sits as dead code in the other role's binary), not a simplification. The only channel shared between the two processes is vcan0; Sensor virtual hw link, Display virtual hw link, and the host clock are each reached by exactly one side.

Three separate destination nodes are drawn on purpose, not one merged “host” box: Can reaches only vcan0, Adc/Dio reach only the sensor line, Display reaches only the display line, and Mcu/Port/Gpt/SysTimer touch the host clock/process but carry no application data. A diagram that merged these into one box would invite the (wrong) reading that sensor/display traffic and CAN traffic share a channel, which the channel separation rules forbid.

Two vertical paths, both mandatory

  • Communication path — SW-C → RTE → Com → PduR → CanIf → CanSM → Can → vcan0. (v2.0: CanSM, not CanIf, now drives Can's controller mode, on ComM's behalf — CanIf's own PDU-level Tx/Rx calls into Can are unchanged.)
  • I/O path — SW-C → RTE → IoHwAb → Adc / Dio / Display → virtual hardware link (sensor line for Adc/Dio, display line for Display — never the same link)

BswM/ComM (v2.0) are also service-layer, shown with dashed arrows above: BswM triggers the driver init/deinit action lists that EcuM used to sequence directly, and arbitrates communication-mode requests, which ComM forwards to CanSM.

The MCAL (bsw/mcal/) is the sole substitution boundary: every host-specific artifact — sockets, file descriptors, clock_gettime, the CAN interface name — lives at or below it. Porting to a real microcontroller means rewriting bsw/mcal/ and nothing else (REQ-ARCH-012). As of v2.0 (Phase 9), this has been done once, for the NXP S32K144 (register-level Mcu/Port/ Gpt/SysTimer/Adc/Dio/Can under bsw/mcal/*_S32K144.c and platform/s32k144/), with no change required outside bsw/mcal/.

reading the arrows correctly

Data flow direction vs. call direction

The diagram above draws arrows as call/dependency direction (“layer X is allowed to call layer Y”), matching the spec’s “May call” table. That is not the same thing as which way the bytes actually move — IOHWAB --> ADC means “IoHwAb is allowed to call into Adc”, not “data flows from IoHwAb to Adc”.

For the sensor input path the two directions are opposite: Adc/Dio are called from above but read their data from below (the virtual hw link), then hand it back up the same call chain via return values. Only the display output path happens to have call direction and data direction pointing the same way.

spec §8.2 — task configuration

Who participates in one transmit/receive cycle

The two diagrams above only show modules that touch the payload. Most of the BSW never touches a payload byte yet is still required for a single transmit/receive cycle to happen at all. This diagram separates the four roles: startup, timing, data, and diagnostics.

Line styles

  • ==>One-shot initialization.
  • <-->Application payload, moving in both directions.
  • -.->A call that carries no payload: a periodic release, a time query, an error report.

What each module contributes

ModuleContribution to one tx/rx cyclePayload?
Mcu Brings up core and clock at startup so a time base can exist at all. Nothing during the cycle. No
Port Configures pins/peripherals before any driver uses them. Nothing during the cycle. No
SysTimer The OS's own dedicated tick source, read by nothing except Os_Counter (REQ-ARCH-014) — a real ECU gives the OS a hardware timer no other module shares, for exactly this reason. No

The practical reading: a payload byte only ever moves through rail 3, but it moves only because rail 2 released the task, and only because rail 1 had already made every module ready. Rails 1, 2 and 4 are what make the data path deterministic and observable rather than merely functional.

spec §9.2 — 19 ordered steps (v1.2)

EcuM initialization order

EcuM_Init follows a fixed order. The order is not arbitrary — each group below can only run once the group above it has finished. Shutdown (§9.3) is the same order reversed, so every module is torn down only after everything that depends on it has already stopped.

  1. Clock first
    nothing runs without a time base
    • 01Initialize the logger
    • 02Mcu_Init, Mcu_InitClock
  2. Then pins
    electrical setup precedes peripheral use
    • 03Port_Init
  3. Then the OS's own clock
    the scheduler must keep time before any module Gpt serves exists (REQ-ARCH-014)
    • 04SysTimer_Init + start the OS tick source
    • 05Os_Counter_Init, zeroed against that tick source
    • 06Gpt_Init + start the general-purpose time base
  4. Then diagnostics
    so later failures are recordable, not silently lost
    • 07Det_Init
    • 08Dem_Init
    • 09Parse command-line (post-build-like) configuration
  5. Then drivers
    bottom-up through the MCAL
    • 10I/O MCAL drivers — Adc_Init/Dio_Init or Display_Init
    • 11Can_Init
  6. Then abstraction
    depends on those drivers being ready
    • 12IoHwAb_Init
  7. Then the stack
    each layer needs the one below it
    • 13CanIf_Init
    • 14PduR_Init
    • 15Com_Init
  8. Finally the RTE
    first layer allowed to reach application code
    • 16Rte_Start
    • 17CAN controller to CAN_CS_STARTED
    • 18Start COM I-PDU group (with init enabled)
    • 19Start OS schedule, enter ECUM_STATE_RUN

Implemented in bsw/services/EcuM/EcuM.c exactly as listed above; verified live by running both ECUs and reading the printed §9.3 step-8 scheduler/DET summary at shutdown.

spec §7.5 — static routes

Data flow between the two ECUs

The layer diagram shows one ECU in isolation. This one shows both ECUs together, walking the same layers in both directions at once: SensorEcu transmitting VehicleStatus (0x180) while simultaneously receiving ClusterStatus (0x181), and vice versa for ClusterEcu.

Both PDUs are equally real data paths. The thick/dotted line style here is used only to tell the two PDUs apart at a glance — it does not mean “mandatory vs. optional” the way it did in the layer diagram above.

Reading this diagram

  • Thick arrows (==>): the 0x180 VehicleStatus path, SensorEcu → ClusterEcu, produced every 20 ms, with a 100 ms reception deadline monitored on the ClusterEcu side.
  • Dotted arrows (-.->): the 0x181 ClusterStatus path, ClusterEcu → SensorEcu, produced every 100 ms, with a 500 ms reception deadline monitored on the SensorEcu side.
  • Every box is used by both flows — Com, PduR, CanIf and Can each run one Tx pipeline for the local ECU’s own PDU and one Rx pipeline for the remote ECU’s PDU. There are not two separate copies of these modules.
  • vcan0 is the only thing the two processes share. Nothing bypasses it — the receiving Com only accepts a frame after CanIf/PduR hand it a fully-formed I-PDU, and only after CRC + alive-counter validation does the RTE buffer update (REQ-COM-003, REQ-RTE-005). A single invalid frame leaves the previous application values untouched.
  • This is the communication path drawn twice (once per direction) and joined at the bus. It does not include the I/O path, which is internal to each ECU and never reaches the other one.

Hướng dẫn cho người mới

Phần này giải thích lại đúng sơ đồ “Data flow between the two ECUs” ở trên bằng phép ví von đời thường, dành cho người mới tiếp cận AUTOSAR muốn nắm mô hình tư duy trước khi nhớ tên module. Giữ nguyên tiếng Việt có chủ đích — viết cho người đọc Việt mới bắt đầu, không phải tài liệu mức đặc tả.

Sơ đồ này nói về việc gì? — dùng phép ví von “gửi thư”

Hãy tưởng tượng 2 ECU là 2 tòa nhà văn phòng, mỗi tòa có nhiều phòng ban xếp chồng lên nhau theo tầng, và giữa 2 tòa có một con đường chung duy nhất để xe chở thư chạy qua lại — đó chính là vcan0.

Đi từng bước một lượt thư “tốc độ xe” từ SensorEcu sang ClusterEcu

Giả sử cảm biến đo được xe đang chạy 120 km/h. Đây là hành trình lá thư đi qua sơ đồ (nhánh nét đậm trong hình):

Trong tòa SensorEcu

  1. 01 VehicleStateSwc (người viết thư) viết nội dung “tốc độ = 12000” (đơn vị 0.01 km/h). Người này không hề biết thư sẽ đi bằng phương tiện gì, địa chỉ ra sao — chỉ đưa cho trợ lý. Rte_Write_PpVehicleState_VehicleSpeedRaw(12000)
  2. 02 RTE (trợ lý riêng) nhận nội dung, chuyển xuống phòng đóng gói theo đúng quy trình nội bộ đã định sẵn. Com_SendSignal
  3. 03 Com (phòng đóng gói) gom nội dung này + trạng thái ignition + một số thứ tự tăng dần (alive counter) + một con tem chống giả mạo (CRC8) vào đúng 1 phong bì 8 byte, cứ 20 ms lại gói và gửi một lần dù nội dung có đổi hay không. I-PDU VehicleStatus
  4. 04 PduR (phòng phân loại) nhìn vào bảng đã treo sẵn trên tường (“PDU này → gửi ra bưu cục theo route số 0”), không đọc nội dung thư, chỉ chuyển tiếp theo địa chỉ đã cấu hình sẵn.
  5. 05 CanIf (bưu cục) dịch “tên gọi nội bộ của thư” thành địa chỉ thật trên đường — ở đây là mã CAN ID 0x180.
  6. 06 Can (bãi xe) bỏ thư lên xe, chạy ra con đường chung.
  7. 07 Xe chạy trên vcan0 — đây là khoảnh khắc duy nhất lá thư rời khỏi tòa nhà SensorEcu.

Trong tòa ClusterEcu

  1. 08 Can bên ClusterEcu đứng ở bãi xe luôn để ý xem có xe nào từ đường chạy vào không — không chặn tiến trình khác (non-blocking).
  2. 09 CanIf nhận thư, thấy CAN ID 0x180 → tra bảng biết đây là PDU nào.
  3. 10 PduR chuyển thư này tới đúng phòng Com phụ trách.
  4. 11 Com xé phong bì: kiểm tra tem chống giả mạo (CRC) trước, rồi kiểm tra số thứ tự có đúng “số liền trước + 1” không. Nếu 1 trong 2 cái sai → vứt cả lá thư, không cập nhật gì hết — đây chính là ý nghĩa dòng chữ “CRC+counter checked” trong sơ đồ.
  5. 12 Nếu thư hợp lệ, Com mới đưa nội dung cho RTE, và RTE mới đưa cho ClusterControlSwc (người đọc thư) — người này đọc được “tốc độ = 12000” và tự quyết định: 120 km/h > ngưỡng 100 km/h → chuyển trạng thái sang OVERSPEED.

Vậy còn nhánh nét chấm là gì?

Đó là lá thư đi chiều ngược lại: ClusterControlSwc viết trạng thái cụm đồng hồ (OFF/NORMAL/OVERSPEED…) rồi gửi ngược về cho SensorEcu biết, qua đúng các phòng ban y hệt nhưng đi ngược chiều, đóng gói thành CAN ID khác (0x181), chu kỳ gửi thưa hơn (100 ms thay vì 20 ms).

Điều thú vị: cùng một phòng Com, một phòng PduR, một bưu cục CanIf, một bãi xe Can — nhưng vừa xử lý thư gửi đi (0x181) vừa xử lý thư nhận vào (0x180). Không phải 2 bộ phòng ban riêng biệt cho 2 chiều. Đó là lý do trong sơ đồ, mỗi ô hình chữ nhật có cả mũi tên nét đậm lẫn nét chấm đi qua nó.

Vì sao phải qua nhiều phòng ban rắc rối vậy, gửi thẳng có được không?

Vì nếu VehicleStateSwc tự mình biết CAN ID là 0x180, tự đóng gói byte, tự gọi socket — thì khi thay đổi loại xe (đổi CAN ID) hoặc đổi hẳn sang chip vi điều khiển thật, ta phải sửa lại code người viết thư. Nhưng với cách chia phòng ban này, người viết thư không bao giờ phải đổi — chỉ có “bưu cục” (CanIf) hay “bãi xe” (Can) cần đổi khi đổi phần cứng. Đây chính là lý do AUTOSAR chia lớp: mỗi lỗi/thay đổi chỉ ảnh hưởng đúng 1 tầng, không lan ra toàn bộ tòa nhà.

Timeout (deadline) nghĩa là gì trong ví dụ này?

Nếu quá 100 ms mà SensorEcu không thấy có thư mới nào từ ClusterEcu bay tới (bình thường 100 ms có 1 thư), SensorEcu sẽ nghĩ “chắc đường dây bị đứt hoặc tòa bên kia sập” → tự báo lỗi DEM_EVENT_CLUSTER_STATUS_TIMEOUT. Tương tự chiều ngược lại, nếu ClusterEcu quá 100 ms không nhận được 0x180, nó sẽ chuyển sang trạng thái COMM_FAULT (mất liên lạc) — thay vì cứ hiển thị mãi tốc độ cũ như không có chuyện gì xảy ra, điều đó rất nguy hiểm trên xe thật.

Tóm gọn 1 câu: sơ đồ này là 2 tòa nhà giống hệt nhau, đứng quay lưng vào nhau, chia sẻ đúng 1 con đường ở tầng trệt, và mỗi tòa vừa gửi thư đi vừa nhận thư về qua đúng các phòng ban đó — không ai trong tòa nhà biết “con đường” trông ra sao, trừ đúng phòng Can ở tầng trệt.

docs/IMPLEMENTATION_STATUS.md

Implementation status

See docs/IMPLEMENTATION_STATUS.md for the full phase-by-phase record. All 8 phases of the v1 spec's section 16 plan are complete (plus the between-4-and-5 SysTimer/Os_Counter split): both ECU executables run their full lifecycle over real vcan0, every section 14.1 unit test and all seven section 14.2 integration tests (IT-01 through IT-07) pass, the project builds and passes its full test suite under AddressSanitizer and UndefinedBehaviorSanitizer with zero diagnostics, and the REQ-ARCH-012 stub-MCAL build is verified.

The layering, routing, and lifecycle behavior described above is therefore the observed behavior of the v1 code, not only its target. docs/REQUIREMENTS_TRACEABILITY.md covers every REQ-* requirement in the v1 specification.

Phase 9 (v2.0 — BswM/ComM/CanSM and the S32K144 hardware port) is in progress, not done. The modules, MCAL drivers, and diagrams above describe the v2.0 target architecture; the code does not yet fully match it. docs/IMPLEMENTATION_STATUS.md's Phase 9 section and docs/REQUIREMENTS_TRACEABILITY.md's Phase 9 section list the specific open violations (in short: BswM's shutdown action list leaks drivers, BswM_DeInit skips cleanup after a failed init, EcuM can claim ECUM_STATE_RUN before BswM_Init succeeds, Os.c reaches into BswM directly, the S32K144 CMake variant still builds the POSIX-only unit tests, and ComM_ModeType is defined twice). Treat the dashed BswM/ComM/CanSM arrows above as the intended contract, not yet a verified one.
